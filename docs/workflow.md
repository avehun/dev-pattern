# Рабочий цикл

Что происходит в сессии с dev-pattern, шаг за шагом, и какой механизм за каждым шагом стоит.
Главный принцип: то, что **должно** случиться, обеспечивает Claude Code (хуки, настройки),
а не память модели. Инструкции модели — только там, где нужно суждение.

## 1. Старт сессии

Хук `SessionStart` подставляет в контекст две вещи:

- **правила** (`plugins/dev-pattern/rules.md`, ~25 строк): сначала база знаний, исследование
  через `researcher`, план всегда, когда отдавать работу `worker`, чем закончить;
- **индекс базы знаний** (`docs/dp/knowledge/INDEX.md`).

Тот же хук снимает «отпечаток» рабочего дерева: id git-дерева, построенного во временном
индексе. По нему в конце хода видно, что изменила именно эта сессия. Твоя незакоммиченная
работа, начатая до сессии, в счёт не идёт.

Почему хук, а не `CLAUDE.md`: плагин не может положить свой `CLAUDE.md`, а трогать `CLAUDE.md`
проекта мы не хотим. Хук срабатывает гарантированно и в проекте ничего не меняет.

В проектах, где `setup` не запускали (нет `docs/dp/knowledge/INDEX.md`), все хуки молчат.
Плагин можно включить глобально, и другие репозитории этого не заметят.

## 2. План

`setup` ставит `permissions.defaultMode: plan`, поэтому каждая сессия начинается в plan mode.
Пока ты не одобришь план, Claude Code сам не даёт править файлы.

План соразмерен задаче. Для опечатки хватит двух строк. Для настоящей работы в нём есть цель,
шаги, файлы, риски, **какие документы обновятся**, как проверить и какие шаги (если есть)
уйдут `worker`.

Если работа займёт несколько сессий, план сохраняется в `docs/dp/plans/<slug>.md` с
чек-листом. Иначе он живёт только в чате, чтобы не засорять репозиторий.

## 3. Исследование

Пока Opus планирует, код читает `researcher` на Sonnet: один конкретный вопрос на вызов,
независимые вопросы идут параллельно. Он:

1. читает индекс и запускает `dp-kb-stale`;
2. если подходящий модуль свежий и отвечает на вопрос, на этом останавливается;
3. иначе дочитывает код, только недостающее;
4. записывает в базу знаний то, что пригодится другой задаче;
5. возвращает короткий отчёт: ответ, `file:line`, что изменилось в базе.

Plan mode запрещает запись и сабагентам. Исследователю запись в `docs/dp/knowledge/`
разрешает guard-хук (`permissionDecision: allow`), и только туда.

## 4. Работа

Код пишет Opus. Отдельный шаг он может отдать `worker` (Sonnet), если шаг полностью
определён, требует узкого контекста и длинный: много файлов или много циклов «правка → тест».
Это объявляется в плане. После `worker` Opus сам смотрит дифф и запускает проверку.
Почему именно так, разобрано в [agents.md](agents.md).

## 5. Документация

Хук `Stop` срабатывает в конце каждого хода и сравнивает отпечаток дерева с тем, что был на
старте сессии:

| Изменилось за сессию | Результат |
| --- | --- |
| ничего, или только документация | ход заканчивается |
| код и документация (`*.md`, `*.mdx`, `*.rst`, `docs/**`) | ход заканчивается |
| код без документации | **блокировка**: Claude получает список файлов и задачу обновить документы и базу знаний |
| код без документации, но есть отказ `dp-docs-waive` для этого состояния | ход заканчивается, причина показывается тебе |
| в изменённом коде есть `TODO(human)` | ход заканчивается: это упражнение `tutor-practice` ждёт тебя |

Подробности:
- Не считаются ни кодом, ни документацией: файлы планов (`docs/dp/plans/`), lock-файлы,
  `.claude/**` и `.gitignore`.
- Отказ привязан к точному состоянию дерева: любая следующая правка требует нового отказа.
- После трёх блокировок подряд хук отпускает ход и предупреждает тебя, чтобы сессия не зациклилась.

## Что где лежит в проекте

```
docs/dp/knowledge/INDEX.md     индекс (подставляется в каждую сессию)
docs/dp/knowledge/<topic>.md   модули базы знаний
docs/dp/plans/<slug>.md        планы многосессионной работы
.git/dp/                       служебное состояние: отпечатки сессий, отказы, манифест установки
```

`.git/dp/` никогда не коммитится.
