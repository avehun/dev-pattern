# Рабочий процесс

Установка, онбординг, уровни автономии и сквозной прогон одной фичи.

## Установка в проект

```bash
git clone https://github.com/avehun/dev-pattern.git ~/dev-pattern
cd /путь/к/проекту
bash ~/dev-pattern/scripts/init.sh .
```

Инсталлятор **никогда не затирает** существующие файлы: если `CLAUDE.md` уже есть,
рядом появится `CLAUDE.dev-pattern.md`, и вы сольёте руками. Посмотреть, что произойдёт,
не записывая ничего:

```bash
bash ~/dev-pattern/scripts/init.sh . --dry-run
```

Это **единственная команда, которую вы запускаете руками**. Дальше открываете Claude Code
в этой папке и разговариваете. Отдельной установки или логина для исполнителя не нужно —
это тот же Claude Code, тот же аккаунт, просто другая модель.

## Онбординг: лид заполняет документы сам

После установки `docs/constitution.md`, `docs/stack.md`, `docs/architecture.md` и
`docs/glossary.md` — ещё шаблоны с плейсхолдерами, а `docs/knowledge/` — пустой каркас.
Заполнять их руками не нужно.

Лид видит плейсхолдеры в начале любой сессии и, прежде чем взяться за что угодно другое,
проводит онбординг (то же самое делает явная команда `/dp:onboard`):

1. **Читает репозиторий.** Манифесты и локфайлы, конфиги линтера и тайпчекера, `Makefile`,
   и главное — CI: что гоняет CI, то и обязано проходить.
2. **Запускает каждую найденную команду** и записывает реальный exit code. Правило жёсткое:
   в конституцию не попадает команда, которую лид не выполнил. Если команда падает — это не
   повод промолчать, а повод спросить вас, оставлять её гейтом или выкинуть.
3. **Составляет карту модулей** — точки входа, границы, один сквозной data flow с якорями
   `file:line`. То же самое, но глубже, уходит в `docs/knowledge/modules/*.md` — это
   стартовое наполнение постоянной памяти проекта (см. [База знаний](knowledge-base.md)).
   Чего не проверил — уходит в раздел `## Not yet mapped`, а не выдумывается.
4. **Задаёт вопросы пачкой**, с уже подставленными вариантами: вы подтверждаете, а не
   сочиняете. Спрашивает только то, чего нет в репозитории — включая нестандартные
   off-limits пути, которые уйдут в `.claude/dp-guard.json`.
5. **Пишет документы** и прогоняет `bash scripts/doctor.sh`.

Ваше участие — минут пять на подтверждения.

Сменился стек — `/dp:onboard --recheck`: лид сверит документы с репозиторием, покажет
расхождения и предложит правку. Написанное человеком он не затирает.

## Уровни автономии

Онбординг спрашивает, насколько самостоятельно работает лид. Ответ живёт в
`docs/constitution.md`, в разделе Delegation policy, и его можно поменять в любой момент:

```
autonomy: supervised        # manual | supervised | auto
executor-model: sonnet
max-attempts: 2
```

| `autonomy` | Лид останавливается |
| --- | --- |
| `manual` | на каждом шаге: печатает команду, запускаете вы |
| `supervised` | подтверждение критериев приёмки → эскалация задачи → финальный quickstart |
| `auto` | только подтверждение критериев приёмки |

**На любом уровне**, включая `auto`, лид останавливается безусловно, когда упал quality gate
и починка неочевидна, когда правка задевает миграции, авторизацию, платежи или удаление
данных, когда нужна новая зависимость и когда просьба противоречит конституции. Автономия —
это про то, что вы не печатаете команды. Это не мандат принимать решения за вас. `git push`
вне зависимости от автономии остаётся под запретом в `.claude/settings.json`.

Начните с `supervised`. Переходите на `auto`, когда две-три фичи подряд прошли без
неожиданностей; возвращайтесь на `manual`, когда хотите посмотреть на исполнителя своими
глазами (например, после смены его модели).

## Как это выглядит в работе

```
$ claude
> надо, чтобы сессии переживали рестарт сервера

Проект ещё не онбординжен — сниму слепок, это займёт пару минут.
[читает package.json, tsconfig.json, .github/workflows/ci.yml]
[запускает npm run lint, npm run typecheck, npm test, npm run build]

Гейты: lint, typecheck, test проходят. build падает на TS2345 в src/api/handler.ts:42.
Четыре вопроса — и я начну фичу.
  ...

[после ответов]
Записал конституцию, стек, карту модулей, глоссарий и первые записи в docs/knowledge/.
doctor.sh зелёный.

Шаг 1/7: исследование. Смотрю docs/knowledge/INDEX.md, потом — чем сейчас хранятся сессии.
...
Шаг 2/7: спека. Вот критерии приёмки, подтвердите:
  AC-1  Given перезапуск сервера, when клиент шлёт валидную куку, then сессия жива
  AC-2  ...
```

Дальше лид сам пишет карточки, вызывает исполнителя через Agent-инструмент, ревьюит и
принимает. Вы читаете вердикты.

## Сквозной прогон

### Шаг 1–4: лид готовит работу

Вы просто сказали, что нужно сделать. Лид сам проходит четыре шага, объявляя каждый одной
строкой. Те же шаги можно вызвать поштучно, если хочется вести процесс руками:

```
/dp:research обновление токенов
/dp:spec token-refresh
/dp:plan
/dp:tasks
```

Все семь шагов подряд — `/dp:feature <что нужно сделать>`. Это ровно то, что лид делает
сам, когда вы описываете задачу словами.

**Здесь вас спросят один раз — про критерии приёмки.** Это единственная остановка, которая
не отключается ни на одном уровне автономии: на `AC-n` ссылаются все карточки, всё ревью и
определение готовности. Ошибка в критерии расходится по всему, что идёт дальше.

После этого в репозитории появилось:

```
docs/specs/001-token-refresh/
├── research.md   plan.md   spec.md   data-model.md
├── contracts/    quickstart.md   checklist.md   tasks.md
└── tasks/T-001.md  T-002.md  T-003.md
```

Посмотреть доску в любой момент:

```bash
bash scripts/status.sh
```

```
autonomy: supervised

001-token-refresh  Token refresh  [spec: ready]  0/3 tasks done
  todo               T-001      Add refresh() to AuthClient
  todo               T-002      Persist refresh token
  todo               T-003      Retry-once middleware   (needs: T-001)

Ready to delegate: T-001 T-002
```

### Шаг 5: передача задачи исполнителю

Делегирование — это лид, вызывающий штатный Agent-инструмент Claude Code, а не отдельный
процесс. Механика в деталях: [`.claude/commands/dp/delegate.md`](../template/.claude/commands/dp/delegate.md).

Коротко:

1. `bash scripts/prepare-delegation.sh T-001` — проверяет карточку (статус, зависимости,
   `allowed_paths`, `verify`, счётчик попыток), и при успехе коммитит незакоммиченное вне
   `.claude/` (исполнитель работает в изолированном git worktree и видит только то, что уже
   в истории), бампает `attempt`, пишет `.claude/dp-active-task.json` — указатель, по
   которому хук понимает, что этой задаче разрешено трогать.
2. Лид сам вызывает Agent-инструмент: `subagent_type` — `dp-implementer` (или `dp-fixer`,
   `dp-test-writer` по полю `agent:` карточки), `isolation: "worktree"`, карточка как
   промпт. Независимые готовые карточки — несколько вызовов Agent одним сообщением, они
   выполняются параллельно.
3. Результату не верят: путь worktree приходит прямо в результате вызова, и лид сам гоняет
   там `git diff --stat`, сверяя изменённые файлы со списком `allowed_paths`.
4. `bash scripts/set-status.sh T-001 in_review`.

При `autonomy: manual` лид на этом шаге останавливается и просит вас подтвердить перед
шагом 2 — на остальных уровнях идёт до конца сам.

### Параллельная работа

Задачи без взаимных зависимостей делегируются одновременно: `prepare-delegation.sh`
запускается по очереди для каждой (у каждой свой коммит и свой указатель), а вызовы
Agent-инструмента для всех отправляются в одном сообщении лида — они реально выполняются
параллельно, каждый в своём изолированном worktree. Без этого задачи выполняются
последовательно — иначе они затрут правки друг друга в общей рабочей копии.

### Шаг 6: ревью

```
/dp:review T-001
```

На `supervised` и `auto` лид переходит к ревью сам, не дожидаясь команды. Он гоняет
`verify` и гейты **в worktree исполнителя**, проверяет критерии приёмки и границы, пишет
`reviews/T-001.md` с вердиктом и продвигает всё общее, что узнал, в `docs/knowledge/`.

При `changes_requested` — доработка агентом `dp-fixer`, которому findings отдаются
приложенным файлом ревью (тот же поток: `prepare-delegation.sh T-001 --agent dp-fixer`,
затем вызов Agent-инструмента). `dp-fixer` чинит **только** пронумерованные findings и
дописывает в отчёт секцию `## Attempt 2`.

При `attempt >= max-attempts` (из конституции, по умолчанию 2) `prepare-delegation.sh`
откажется запускаться: это сигнал эскалации. На `manual` и `supervised` лид здесь
останавливается и спрашивает вас. Лид дробит карточку на две-три или берёт задачу себе,
записав причину в `tasks.md`.

### Шаг 7: приёмка

```
/dp:accept T-001
```

Финальный прогон гейтов, коммит `T-001: <название>`, мерж ветки worktree
(`worktreeBranch` из результата делегирования) в текущую и её удаление, `status: done`,
обновление доски и затронутых документов — включая `docs/knowledge/`, если приёмка
подтвердила или поправила что-то в уже записанном.

## Состояния карточки

```
   todo ──► in_progress ──► in_review ──┬──► done
     ▲            │                     │
     │            ▼                     ▼
     │        blocked           changes_requested
     │                                  │
     └───────────── fixer ◄─────────────┘
                    │
                    ▼  attempt >= max-attempts
                escalated ──► лид дробит карточку или делает сам
```

| Статус | Кто ставит | Что значит |
| --- | --- | --- |
| `todo` | лид | готова к делегированию |
| `in_progress` | `prepare-delegation.sh` | исполнитель работает |
| `in_review` | `set-status.sh` (лид, после делегирования) | работа сдана, ждёт лида |
| `changes_requested` | лид | есть findings, нужен `dp-fixer` |
| `blocked` | исполнитель | карточка неполна, нужен лид |
| `escalated` | лид | превышен `max-attempts` |
| `done` | лид | принято и закоммичено |

## Шпаргалка

Обычно вам ничего из этого не нужно — команды гоняет лид. Список на случай, когда хочется
посмотреть самому или вы работаете на `autonomy: manual`.

```bash
bash scripts/doctor.sh                        # всё ли настроено
bash scripts/status.sh                        # доска задач и уровень автономии
bash scripts/new-feature.sh <слаг>            # новая фича из шаблонов
bash scripts/prepare-delegation.sh T-001      # валидация + подготовка к делегированию
bash scripts/set-status.sh T-001 in_review    # смена статуса карточки
```

Слэш-команды в Claude Code:

```
/dp:onboard          заполнить документы проекта (--recheck — сверить с кодом)
/dp:feature <что>    весь цикл от исследования до приёмки
/dp:status           состояние доски
```

Остальные — `/dp:research`, `/dp:spec`, `/dp:plan`, `/dp:tasks`, `/dp:delegate`,
`/dp:review`, `/dp:accept` — нужны, только если вы ведёте процесс поштучно.
