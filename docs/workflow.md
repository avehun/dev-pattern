# Рабочий процесс

Установка, онбординг, уровни автономии и сквозной прогон одной фичи.

## Установка в проект

```bash
git clone https://github.com/avehun/dev-pattern.git ~/dev-pattern
cd /путь/к/проекту
bash ~/dev-pattern/scripts/init.sh .
```

Инсталлятор **никогда не затирает** существующие файлы: если `CLAUDE.md` уже есть,
рядом появится `CLAUDE.dev-pattern.md`, и вы сольёте руками. Посмотреть, что произойдёт,
не записывая ничего:

```bash
bash ~/dev-pattern/scripts/init.sh . --dry-run
```

Это **единственная команда, которую вы запускаете руками**. Дальше открываете Claude Code
в этой папке и разговариваете.

## Онбординг: лид заполняет документы сам

После установки `docs/constitution.md`, `docs/stack.md`, `docs/architecture.md` и
`docs/glossary.md` — ещё шаблоны с плейсхолдерами. Заполнять их руками не нужно.

Лид видит плейсхолдеры в начале любой сессии и, прежде чем взяться за что угодно другое,
проводит онбординг (то же самое делает явная команда `/dp:onboard`):

1. **Читает репозиторий.** Манифесты и локфайлы, конфиги линтера и тайпчекера, `Makefile`,
   и главное — CI: что гоняет CI, то и обязано проходить.
2. **Запускает каждую найденную команду** и записывает реальный exit code. Правило жёсткое:
   в конституцию не попадает команда, которую лид не выполнил. Если команда падает — это не
   повод промолчать, а повод спросить вас, оставлять её гейтом или выкинуть.
3. **Составляет карту модулей** — точки входа, границы, один сквозной data flow с якорями
   `file:line`. Чего не проверил — уходит в раздел `## Not yet mapped`, а не выдумывается.
4. **Задаёт вопросы пачкой**, с уже подставленными вариантами: вы подтверждаете, а не
   сочиняете. Спрашивает только то, чего нет в репозитории.
5. **Пишет документы** и прогоняет `bash scripts/doctor.sh`.

Ваше участие — минут пять на подтверждения. Единственное, что придётся сделать самому:
`opencode auth login`, если ещё не авторизованы.

Сменился стек — `/dp:onboard --recheck`: лид сверит документы с репозиторием, покажет
расхождения и предложит правку. Написанное человеком он не затирает.

## Уровни автономии

Онбординг спрашивает, насколько самостоятельно работает лид. Ответ живёт в
`docs/constitution.md`, в разделе Delegation policy, и его можно поменять в любой момент:

```
autonomy: supervised        # manual | supervised | auto
executor-model: opencode/grok-code
max-attempts: 2
```

| `autonomy` | Лид останавливается |
| --- | --- |
| `manual` | на каждом шаге: печатает команду, запускаете вы (поведение из режима A ниже) |
| `supervised` | подтверждение критериев приёмки → эскалация задачи → финальный quickstart |
| `auto` | только подтверждение критериев приёмки |

**На любом уровне**, включая `auto`, лид останавливается безусловно, когда упал quality gate
и починка неочевидна, когда правка задевает миграции, авторизацию, платежи или удаление
данных, когда нужна новая зависимость и когда просьба противоречит конституции. Автономия —
это про то, что вы не печатаете команды. Это не мандат принимать решения за вас.

Начните с `supervised`. Переходите на `auto`, когда две-три фичи подряд прошли без
неожиданностей; возвращайтесь на `manual`, когда меняете модель исполнителя и хотите
посмотреть на неё своими глазами.

## Как это выглядит в работе

```
$ claude
> надо, чтобы сессии переживали рестарт сервера

[запускает npm run lint, npm run typecheck, npm test, npm run build]

Гейты: lint, typecheck, test проходят. build падает на TS2345 в src/api/handler.ts:42.
Четыре вопроса — и я начну фичу.
  ...

[после ответов]
Записал конституцию, стек, карту модулей и глоссарий. doctor.sh зелёный.

Шаг 1/7: исследование. Смотрю, чем сейчас хранятся сессии.
```

Дальше лид сам гоняет `new-feature.sh`, `delegate.sh`, `status.sh`, ревью и приёмку.
Вы читаете вердикты.

## Сквозной прогон

### Шаг 1–4: лид готовит работу

Вы просто сказали, что нужно сделать. Лид сам проходит четыре шага, объявляя каждый одной
строкой. Те же шаги можно вызвать поштучно, если хочется вести процесс руками:

```
/dp:research обновление токенов
/dp:spec token-refresh
/dp:plan
/dp:tasks
```

Все семь шагов подряд — `/dp:feature <что нужно сделать>`. Это ровно то, что лид делает
сам, когда вы описываете задачу словами.

**Здесь вас спросят один раз — про критерии приёмки.** Это единственная остановка, которая
не отключается ни на одном уровне автономии: на `AC-n` ссылаются все карточки, всё ревью и
определение готовности. Ошибка в критерии расходится по всему, что идёт дальше.

После этого в репозитории появилось:

```
docs/specs/001-token-refresh/
├── research.md   plan.md   spec.md   data-model.md
├── contracts/    quickstart.md   checklist.md   tasks.md
└── tasks/T-001.md  T-002.md  T-003.md
```

Посмотреть доску в любой момент:

```bash
bash scripts/status.sh
```

```
autonomy: supervised

001-token-refresh  Token refresh  [spec: ready]  0/3 tasks done
  todo               T-001      Add refresh() to AuthClient
  todo               T-002      Persist refresh token
  todo               T-003      Retry-once middleware   (needs: T-001)

Ready to delegate: T-001 T-002
```

### Шаг 5: передача задачи исполнителю

Что здесь происходит, решает `autonomy` из конституции.

#### `supervised` и `auto` — запускает лид

```bash
bash scripts/delegate.sh T-001 --auto
```

Лид валидирует карточку, запускает opencode, дожидается результата и докладывает, что
изменилось. Вы ничего не печатаете.

`--auto` здесь **обязателен, а не ускорение**. Без него `opencode run` встаёт и ждёт, пока
человек подтвердит каждую правку, — а в сессии, которую ведёт лид, отвечать некому, и запуск
висит до тех пор, пока его не убьют. Начиная с этой версии `delegate.sh` отказывается
стартовать без TTY и без `--auto`, вместо того чтобы зависнуть молча.

Прав это не добавляет: **`deny`-правила из `opencode.json` продолжают действовать**. За
`allowed_paths` исполнитель не выйдет, в `docs/` не попадёт, git ему по-прежнему закрыт.

#### `manual` — запускаете вы

```
/dp:delegate T-001
```

Лид валидирует карточку и печатает готовую команду:

```bash
bash scripts/delegate.sh T-001
```

opencode стартует и спрашивает подтверждение на каждую правку — вы видите всё, что он
делает. Полезно на первых задачах и при смене модели исполнителя.

При `autonomy: manual` `delegate.sh` откажется принимать `--auto` без `--force`: раз вы
попросили смотреть глазами, скрипт не даст лиду обойти это молча.

#### Что делает `delegate.sh`

1. Проверяет карточку: статус, зависимости (`depends_on` все `done`), наличие
   `verify` и `allowed_paths`, счётчик попыток, отсутствие отсылок «смотри план».
2. Создаёт ветку `task/T-001` (или worktree при `--worktree`).
3. Ставит `status: in_progress`, инкрементирует `attempt`.
4. Запускает `opencode run --agent implementer -f <карточка> "<задание>"`.
5. По завершении ставит `status: in_review` и показывает `git diff --stat`.

Проверить команду, ничего не запуская:

```bash
bash scripts/delegate.sh T-001 --dry-run
```

### Параллельная работа

Задачи без взаимных зависимостей можно гнать одновременно в изолированных worktree:

```bash
bash scripts/delegate.sh T-001 --worktree --auto &
bash scripts/delegate.sh T-002 --worktree --auto &
```

Каждая получит свою копию рабочего дерева в `.worktrees/T-00X` и свою ветку. Без
`--worktree` задачи выполняются последовательно — иначе они затрут правки друг друга.

### Шаг 6: ревью

```
/dp:review T-001
```

На `supervised` и `auto` лид переходит к ревью сам, не дожидаясь команды. Он гоняет
`verify` и гейты, проверяет критерии приёмки и границы, пишет
`reviews/T-001.md` с вердиктом.

При `changes_requested` — доработка агентом `fixer`, которому findings отдаются
приложенным файлом:

```bash
bash scripts/delegate.sh T-001 --agent fixer --review --auto
```

`fixer` чинит **только** пронумерованные findings и дописывает в отчёт секцию
`## Attempt 2`.

При `attempt >= max-attempts` (из конституции, по умолчанию 2) `delegate.sh` откажется
запускаться: это сигнал эскалации. На `manual` и `supervised` лид здесь останавливается и
спрашивает вас.
Лид дробит карточку на две-три или берёт задачу себе, записав причину в `tasks.md`.

### Шаг 7: приёмка

```
/dp:accept T-001
```

Гейты, коммит `T-001: <название>`, мерж ветки, `status: done`, обновление доски и
затронутых документов.

## Состояния карточки

```
   todo ──► in_progress ──► in_review ──┬──► done
     ▲            │                     │
     │            ▼                     ▼
     │        blocked           changes_requested
     │                                  │
     └──────────── fixer ◄──────────────┘
                    │
                    ▼  attempt >= max-attempts
                escalated ──► лид дробит карточку или делает сам
```

| Статус | Кто ставит | Что значит |
| --- | --- | --- |
| `todo` | лид | готова к делегированию |
| `in_progress` | `delegate.sh` | исполнитель работает |
| `in_review` | `delegate.sh` | работа сдана, ждёт лида |
| `changes_requested` | лид | есть findings, нужен `fixer` |
| `blocked` | исполнитель | карточка неполна, нужен лид |
| `escalated` | лид | две неудачные попытки |
| `done` | лид | принято и закоммичено |

## Шпаргалка

Обычно вам ничего из этого не нужно — команды гоняет лид. Список на случай, когда хочется
посмотреть самому или вы работаете на `autonomy: manual`.

```bash
bash scripts/doctor.sh                       # всё ли настроено
bash scripts/status.sh                       # доска задач и уровень автономии
bash scripts/new-feature.sh <слаг>           # новая фича из шаблонов
bash scripts/delegate.sh T-001 --dry-run     # что будет запущено
bash scripts/delegate.sh T-001               # с подтверждением каждой правки
bash scripts/delegate.sh T-001 --auto        # без подтверждений; так запускает лид
bash scripts/delegate.sh T-001 --worktree    # в изолированном worktree
bash scripts/delegate.sh T-001 --agent fixer --review --auto   # доработка по ревью
```

Слэш-команды в Claude Code:

```
/dp:onboard          заполнить документы проекта (--recheck — сверить с кодом)
/dp:feature <что>    весь цикл от исследования до приёмки
/dp:status           состояние доски
```

Остальные — `/dp:research`, `/dp:spec`, `/dp:plan`, `/dp:tasks`, `/dp:delegate`,
`/dp:review`, `/dp:accept` — нужны, только если вы ведёте процесс поштучно.
