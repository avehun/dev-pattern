# Агенты и экономия

В сессии три участника:

| Кто | Модель | Что делает |
| --- | --- | --- |
| основная сессия | Opus | решает, планирует, пишет код, проверяет |
| `researcher` | Sonnet | читает код, отвечает на вопрос, ведёт базу знаний |
| `worker` | Sonnet | механические правки по чёткому заданию |

`setup` ставит `model: opus` для основной сессии. Сабагенты закреплены на Sonnet в своём
фронтматтере (это проверяет `check.sh`).

## Почему исследование на Sonnet, а код — нет

Цены за 1M токенов (API, октябрь 2026):

| | ввод | вывод | чтение из кэша |
| --- | --- | --- | --- |
| Opus 5.5 | $4 | $20 | $0.20 |
| Sonnet 5.5 | $2 | $10 | $0.20 |

**Исследование выгодно отдавать всегда.** Это самая «прожорливая» часть: сотни прочитанных
строк. В отдельном контексте Sonnet их читает вдвое дешевле, а в контекст Opus попадает
только выжимка. Ещё важнее, что основной контекст не засоряется: длинная сессия дольше
остаётся «умной».

**С кодом всё не так очевидно.** Разница в цене всего двукратная, а у делегирования есть
накладные расходы:

1. Opus пишет задание: это вывод Opus, самые дорогие токены.
2. Sonnet стартует с пустым контекстом и заново читает файлы, которые у Opus уже лежат в
   кэше и обходятся ему почти бесплатно (кэш стоит одинаково).
3. Opus читает результат и проверяет дифф.
4. При ошибке — переделка.

На обычной правке в 100–300 строк эти расходы съедают выигрыш.

**Когда делегировать всё-таки выгодно.** Главная статья расходов в длинной работе — не вывод,
а **число шагов, умноженное на размер контекста**: каждый вызов инструмента заново оплачивает
весь контекст сессии. Двадцать циклов «тест → правка» при контексте 150k стоят Opus около
3M входных токенов, а `worker` с узким контекстом проходит их в разы дешевле.

Поэтому `worker` получает шаг, только если:
- шаг полностью определён (план уже решил, *что* делать);
- нужен узкий контекст: несколько файлов, а не весь разговор;
- шаг длинный: много файлов или много циклов.

Решение объявляется в плане. Проверка за `worker` обязательна и дешёвая: Opus сам
смотрит дифф и запускает команду проверки.

## Границы (guard-хук)

`plugins/dev-pattern/scripts/guard.sh` срабатывает на PreToolUse и смотрит только на вызовы
этих двух сабагентов (`agent_type` = `dev-pattern:researcher` / `dev-pattern:worker`):

| | researcher | worker |
| --- | --- | --- |
| Запись файлов | только `docs/dp/knowledge/*.md`, **разрешена даже в plan mode** | любой файл репозитория, кроме `docs/`, `.claude/`, `CLAUDE.md`, `.git/`, манифестов и lock-файлов зависимостей; не за пределами репозитория |
| Bash | **только разрешённый список** команд на чтение: `git log/show/diff/blame/ls-files/rev-parse/status`, `dp-kb-stale`, `cat`, `head`, `tail`, `wc`, `ls`, `grep`, `cd`, `pwd` (можно через `;` `&&` `\|`) — без запроса разрешения; перенаправления, `$(…)`, `--output` и всё остальное запрещено | всё, кроме меняющих состояние git-команд и установки пакетов |

Как устроен guard:
- **Fail-open.** При внутренней ошибке (нет `jq`, кривой вход) хук пропускает вызов, и
  действует обычная система разрешений Claude Code. Сломанный хук не должен блокировать работу.
- **Разрешённый список для исследователя, а не запрещённый.** Живой прогон показал: plan mode
  не мешает писать файлы через Bash, и исследователь, считая `Write` запрещённым, записал базу
  знаний через heredoc и `sed -i`. Запрещённый список такие обходы не ловит, поэтому
  исследователю разрешено только перечисленное.
- **Не песочница.** Разбор Bash-команд наивный: кавычки не разбираются. У `worker` запрещённый
  список, и `bash -c "..."` его обойдёт. Guard защищает от случайных ошибок сабагента, а не
  от злоумышленника.

Меняешь guard — обнови эту таблицу и тесты в разделе 3 `scripts/check.sh`.
