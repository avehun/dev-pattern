# Тестирование

Тесты — не отдельный этап, а часть определения «готово». Задача без тестов не проходит
ревью, если только в карточке явно не написано обратное.

## Quality gates

Единственный источник правды — `docs/constitution.md`. Там четыре команды:

```bash
# lint
# typecheck
# test
# build
```

Их гоняют оба агента и на них ссылается каждая карточка. Правила простые:

- **Ни один гейт не «почти зелёный».** Либо ноль, либо не готово.
- **Гейт нельзя отключить, пропустить или продавить `--force`.** Если гейт неправильный,
  это отдельная задача лида, а не решение исполнителя.
- **Гейты должны быть быстрыми.** Если полный прогон занимает пять минут, `verify`
  в карточке сужается до конкретного файла, а полные гейты остаются на приёмку.

`doctor.sh` проверяет, что плейсхолдеры в конституции заменены на настоящие команды —
пока это не сделано, карточки писать бессмысленно.

## Пирамида

| Уровень | Кто пишет | Когда | Сколько |
| --- | --- | --- | --- |
| Unit | исполнитель, в той же задаче | всегда | основная масса |
| Integration | исполнитель, отдельной задачей | для связок между модулями | заметно меньше |
| E2E / ручная проверка | лид, через `quickstart.md` | на приёмке фичи | единицы |

Слабые модели хорошо пишут unit-тесты по чёткой постановке и плохо — интеграционные,
где нужен контекст всей системы. Поэтому интеграционные тесты либо выносятся в отдельную
карточку с максимально подробным Context, либо пишутся лидом.

## Что должно быть в тестах

Каждый тест обязан падать, если удалить проверяемое поведение. Это единственный
надёжный критерий осмысленности.

Обязательно покрываются:

- happy path — по одному на критерий приёмки;
- граничные значения: пусто, ноль, один, максимум;
- пути ошибок — то, что модели пропускают чаще всего;
- инварианты из `data-model.md`.

Явно запрещено:

- `expect(true).toBe(true)` и его родственники;
- тесты, проверяющие моки вместо поведения;
- ослабление ассерта, чтобы «стало зелёно»;
- удаление или `skip` падающего теста.

Последние два пункта — в списке жёстких запретов конституции, и ревью проверяет их
по диффу отдельно.

## Как это связано с карточкой

Поле `verify` — самая узкая команда, которая доказывает, что задача сделана:

```yaml
verify: "npm test -- src/auth/client.test.ts"
```

Не `npm test` на весь проект: долго, и падение в чужом модуле собьёт исполнителя
с толку — он полезет чинить то, что ему не принадлежит.

Перед делегированием лид **сам запускает** `verify` на текущем коде. Она должна падать —
и падать именно по той причине, которую задача устраняет. Если она падает по другой
причине или проходит, карточка написана неверно.

## Агент `dp-test-writer`

Отдельный сабагент для задач, где нужны только тесты. «Прод-код он изменить не может» —
это не отдельная система прав, а тот же хук `dp-guard.sh`, что и у остальных: лид просто
пишет в карточку `allowed_paths`, состоящий только из тестовых файлов, и хук физически не
пустит правку куда-то ещё, независимо от того, какой из трёх сабагентов её пытается сделать.

Если тест падает из-за бага в прод-коде, `dp-test-writer` не чинит его, а пишет
`outcome: blocked` с указанием файла и строки. Это находка для лида, а не работа
исполнителя.

Типичная связка:

```
T-004  dp-implementer   реализация            verify: тест из T-005 ещё не существует
T-005  dp-test-writer   покрытие T-004        depends_on: [T-004]
```

## Definition of Done

Задача считается сделанной, когда:

- [ ] `verify` из карточки завершается кодом 0;
- [ ] все четыре гейта из конституции — зелёные;
- [ ] каждый `AC-n` карточки закрыт с доказательством `file:line`;
- [ ] тесты покрывают happy path, границы и ошибки;
- [ ] изменения только внутри `allowed_paths`;
- [ ] новых зависимостей нет;
- [ ] отчёт `reports/T-XXX.md` содержит **реальный** вывод команды и её код возврата;
- [ ] лид перезапустил проверки сам и увидел то же самое.

Фича считается сделанной, когда закрыты все задачи, `quickstart.md` пройден руками,
а `architecture.md` и `stack.md` обновлены.

## Отчёту не верят

Лид всегда перезапускает `verify` и гейты сам. Не из недоверия к конкретной модели:
слабая модель может честно ошибиться в том, что она видела, а может «дорисовать»
правдоподобный вывод команды.

Если в отчёте написано «passed», а команда падает — это отдельная находка в ревью,
и она важнее самого бага: значит, отчётам этой модели нельзя верить и стоит понизить
её роль или сузить карточки.
