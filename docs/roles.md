# Роли и зоны ответственности

Два агента, одна кодовая база — оба Claude Code, на разных моделях: лид на Opus, исполнитель
на Sonnet. Разделение держится на трёх вещах: явной матрице ответственности, инструкциях в
`CLAUDE.md` и в файлах сабагентов исполнителя, и — главное — **правах доступа**, которые не
зависят от того, послушалась модель инструкции или нет.

## Матрица

| Область | Claude Code (лид, Opus) | Claude Code (исполнитель, Sonnet) |
| --- | --- | --- |
| Исследование кодовой базы и внешних решений | **владеет** | запрещено |
| `docs/constitution.md`, `architecture.md`, ADR | **владеет** | только чтение |
| `spec.md`, `plan.md`, `data-model.md`, `contracts/` | **владеет** | только чтение |
| `docs/knowledge/` (постоянная память проекта) | **владеет** | только чтение |
| Карточки задач `tasks/T-XXX.md` | **владеет** | только чтение |
| Прод-код | по эскалации | **владеет** |
| Тесты | задаёт требования | **владеет** |
| Отчёт `reports/T-XXX.md` | читает | **владеет** |
| Ревью, вердикт, findings | **владеет** | запрещено |
| Зависимости, миграции, CI | **владеет** | запрещено |
| git: коммит, ветки, мерж, пуш | **владеет** | запрещено |
| Общение с пользователем о требованиях | **владеет** | запрещено |
| Онбординг: конституция, стек, карта модулей, глоссарий | **владеет** | только чтение |
| Запуск команд процесса (`prepare-delegation.sh`, `status.sh`, гейты) | **владеет** | запрещено |

Читается так: у каждой строки ровно один владелец. Если оба «как бы могут» — значит
граница не проведена и рано или поздно они затрут работу друг друга.

## Почему лид не пишет код

Не из принципа, а из экономики и из качества постановки.

1. **Экономика.** Дорогая модель тратится на то, чего Sonnet не сделает так же хорошо:
   понять предметную область, найти существующее решение в репозитории, выбрать между тремя
   вариантами, заметить, что тест ничего не проверяет.
2. **Качество постановки.** Пока лид сам пишет код, он не замечает, что его постановка
   дырявая — он держит контекст в голове. Как только код пишет другой агент, любая
   недосказанность немедленно всплывает как проваленная задача. Это обратная связь,
   которая улучшает декомпозицию.
3. **Ревью со стороны.** Автор кода — плохой ревьюер собственного кода. Разделение даёт
   настоящее второе мнение бесплатно.

## Единственное исключение — эскалация

Лид берёт задачу себе, когда:

- пользователь прямо попросил, **или**
- `attempt >= max-attempts` (из конституции, по умолчанию 2): исполнитель не прошёл ревью,
  **или**
- правка мельче карточки, которая бы её описывала: опечатка, переименование, однострочник
  без изменения поведения. Всё, где есть решение о том, как делать, — не этот случай,
  сколько бы строк оно ни занимало.

Перед тем как брать задачу себе, лид обязан сначала попробовать **раздробить карточку**.
Эскалация почти всегда означает не «модель не справилась», а «карточка была слишком
большой» или «в разделе Context не хватало данных». Каждая эскалация записывается строкой
в `tasks.md` с причиной — это статистика о качестве вашей декомпозиции.

## Как границы принуждаются

Инструкция — это просьба. Права — это факт. Claude Code не даёт сабагенту точечных прав
по путям файлов на уровне его собственного фронтматтера (`tools:` там — это список ИМЁН
инструментов целиком: Edit да/нет, а не «Edit, но только в src/»). Поэтому границы
исполнителя держатся на **PreToolUse-хуке**.

### Исполнитель: `.claude/hooks/dp-guard.sh`

Хук получает в stdin JSON с полем `agent_type` — именем сабагента (`dp-implementer`,
`dp-fixer`, `dp-test-writer`), которое присутствует, только когда вызов идёт из
сабагента. У самого лида этого поля нет — хук его не трогает вообще.

Для исполнителя, по порядку:

1. точный путь его собственного отчёта — разрешён (единственное исключение внутри `docs/`);
2. статический deny-лист — всегда: `docs/**`, `.claude/**`, `CLAUDE.md`, `.git/**`,
   манифесты и лок-файлы зависимостей;
3. доп. deny-лист проекта — `.claude/dp-guard.json` (`extra_deny`), заполняется на онбординге;
4. `allowed_paths` активной задачи — из `.claude/dp-active-task.json`, который лид пишет
   перед делегированием; если файла нет — запрещено всё (fail closed).

Для Bash — запрещены `git commit/push/checkout/switch/reset/rebase/stash/merge` и
install/add-команды пакетных менеджеров; всё остальное (тесты, линт, сборка) разрешено —
без этого исполнитель не сможет прогнать `verify`.

Что это даёт на практике:

- исполнитель не может переписать спеку, план, `docs/knowledge/` или собственную инструкцию;
- единственное исключение — его собственный отчёт;
- он не может добавить зависимость;
- он не может коммитить и переключать ветки — а раз он работает в изолированном git
  worktree (`isolation: "worktree"` у Agent-инструмента), это ещё и физически не задевает
  вашу рабочую копию;
- блокировка не зависит от того, что написано в карточке — это отдельный, принудительный
  слой, а не второй экземпляр той же просьбы.

Проверить, что хук действительно работает — самопроверка репозитория (`scripts/check.sh`)
прогоняет его синтетическими вызовами и ждёт конкретных кодов возврата; то же можно сделать
руками:

```bash
echo '{"agent_type":"dp-implementer","tool_name":"Edit","tool_input":{"file_path":"docs/constitution.md"}}' \
  | bash .claude/hooks/dp-guard.sh; echo "exit=$?"   # ожидаем 2
```

### Лид: `.claude/settings.json`

```json
{
  "model": "opus",
  "permissions": {
    "ask":   ["Edit(src/**)", "Write(src/**)", "Edit(lib/**)", "Write(lib/**)"],
    "allow": ["Bash(git commit:*)", "Bash(git switch:*)", "Bash(git merge:*)",
              "Bash(scripts/prepare-delegation.sh:*)", "Bash(scripts/set-status.sh:*)"],
    "deny":  ["Bash(git push:*)", "Read(./.env)"]
  }
}
```

`"model": "opus"` пиннит лида — сессия, открытая в этом проекте, по умолчанию работает на
сильной модели вне зависимости от глобальных настроек пользователя.

Лид **спрашивает** перед записью прод-кода. Это не запрет, а стоп-кран: в момент, когда
он собирается «просто быстро поправить», пользователь видит вопрос и может ответить
«нет, напиши карточку».

Всё, что нужно самому процессу, наоборот **разрешено без вопросов**: git-операции приёмки
(`commit`, `switch`, `merge`) и скрипты процесса. Иначе автономия упирается в запрос
разрешения на каждом `/dp:accept`, а это ровно те команды, которые вы и просили не печатать.
`git push` остаётся в `deny`: публикация — ваше решение, не его.

**Строгий режим.** Если хочется настоящей границы вокруг кода — перенесите строки из `ask`
в `deny`. Тогда лид физически не сможет писать код, и эскалация всегда будет означать
дробление карточки. Минус: при реально сложной задаче процесс упрётся; снимать `deny`
придётся вручную.

**Никогда не запускайте сессию лида с `--dangerously-skip-permissions`** или любым
эквивалентным обходом. Сабагент, которого спавнит лид, наследует эффективный режим прав
родительской сессии — если у лида права обойдены, хук может не сработать и у исполнителя
тоже. Пиннинг `"model": "opus"` этого не заменяет.

## Автономия лида

Права отвечают на вопрос «что лид может сделать». Автономия — на вопрос «где он обязан
остановиться и спросить». Это разные вещи, и настраиваются они в разных местах: права в
`.claude/settings.json` и `.claude/hooks/dp-guard.sh` (+ `dp-guard.json`), автономия — в
`docs/constitution.md`:

```
autonomy: supervised        # manual | supervised | auto
max-attempts: 2
```

| `autonomy` | Остановки |
| --- | --- |
| `manual` | каждый шаг: лид печатает команду, запускаете вы |
| `supervised` | критерии приёмки → эскалация (`attempt >= max-attempts`) → финальный quickstart |
| `auto` | только критерии приёмки |

Безусловные остановки действуют на всех уровнях: упавший quality gate с неочевидной
починкой, миграции, авторизация, платежи, удаление данных, новая зависимость, конфликт
с конституцией. `auto` означает «не спрашивай, какую команду запустить», а не «решай за
меня, что считать готовым».

## Сигналы, что разделение сломалось

- Лид всё чаще правит код сам → карточки слишком крупные, вернитесь к `/dp:tasks`.
- Исполнитель регулярно пишет `outcome: blocked` → в разделе Context не хватает данных или
  ссылок на `docs/knowledge/`.
- Ревью проходит с первого раза всегда → карточки слишком мелкие, вы теряете скорость.
- В `git status` (в worktree исполнителя) файлы, которых нет в `allowed_paths` → хук не
  сработал, проверьте `bash scripts/doctor.sh` и синтетический тест выше.
