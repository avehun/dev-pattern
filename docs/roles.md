# Роли и зоны ответственности

Два агента, одна кодовая база. Разделение держится на трёх вещах: явной матрице
ответственности, инструкциях в `CLAUDE.md` и `AGENTS.md`, и — главное — **правах доступа**,
которые не зависят от того, послушалась модель инструкции или нет.

## Матрица

| Область | Claude Code (лид) | opencode (исполнитель) |
| --- | --- | --- |
| Исследование кодовой базы и внешних решений | **владеет** | запрещено |
| `docs/constitution.md`, `architecture.md`, ADR | **владеет** | только чтение |
| `spec.md`, `plan.md`, `data-model.md`, `contracts/` | **владеет** | только чтение |
| Карточки задач `tasks/T-XXX.md` | **владеет** | только чтение |
| Прод-код | по эскалации | **владеет** |
| Тесты | задаёт требования | **владеет** |
| Отчёт `reports/T-XXX.md` | читает | **владеет** |
| Ревью, вердикт, findings | **владеет** | запрещено |
| Зависимости, миграции, CI | **владеет** | запрещено |
| git: коммит, ветки, мерж, пуш | **владеет** | запрещено |
| Общение с пользователем о требованиях | **владеет** | запрещено |

Читается так: у каждой строки ровно один владелец. Если оба «как бы могут» — значит
граница не проведена и рано или поздно они затрут работу друг друга.

## Почему лид не пишет код

Не из принципа, а из экономики и из качества постановки.

1. **Экономика.** Дорогая модель тратится на то, что бесплатная не умеет: понять
   предметную область, найти существующее решение в репозитории, выбрать между тремя
   вариантами, заметить, что тест ничего не проверяет.
2. **Качество постановки.** Пока лид сам пишет код, он не замечает, что его постановка
   дырявая — он держит контекст в голове. Как только код пишет другой агент, любая
   недосказанность немедленно всплывает как проваленная задача. Это обратная связь,
   которая улучшает декомпозицию.
3. **Ревью со стороны.** Автор кода — плохой ревьюер собственного кода. Разделение даёт
   настоящее второе мнение бесплатно.

## Единственное исключение — эскалация

Лид берёт задачу себе, когда:

- пользователь прямо попросил, **или**
- `attempt >= 2`: исполнитель дважды не прошёл ревью.

Перед тем как брать задачу себе, лид обязан сначала попробовать **раздробить карточку**.
Эскалация почти всегда означает не «модель тупая», а «карточка была слишком большой» или
«в разделе Context не хватало данных». Каждая эскалация записывается строкой в `tasks.md`
с причиной — это статистика о качестве вашей декомпозиции.

## Как границы принуждаются

Инструкция — это просьба. Права — это факт. Поэтому зоны продублированы в конфигах.

### Исполнитель: `opencode.json`

```json
"permission": {
  "edit": {
    "*": "allow",
    "docs/**": "deny",
    "docs/specs/*/reports/**": "allow",
    "CLAUDE.md": "deny",
    "AGENTS.md": "deny",
    "opencode.json": "deny",
    ".claude/**": "deny",
    ".opencode/**": "deny"
  },
  "bash": {
    "*": "ask",
    "git commit*": "deny",
    "git push*": "deny",
    "npm install*": "deny"
  },
  "webfetch": "deny",
  "websearch": "deny"
}
```

Что это даёт на практике:

- исполнитель не может переписать спеку, план или собственную инструкцию;
- единственное исключение — его собственный отчёт в `reports/`;
- он не может добавить зависимость (запрещены `npm install`, `pip install`, `cargo add`
  и правки манифестов и лок-файлов);
- он не может коммитить и переключать ветки — значит лид всегда видит чистый рабочий
  дифф и сам решает, что попадёт в историю;
- у него нет доступа в сеть: весь контекст обязан быть в карточке.

Проверить, что правила действительно применились:

```bash
opencode agent list | sed -n '/^implementer (/,/^test-writer (/p' | grep -A2 '"docs/\*\*"'
```

### Лид: `.claude/settings.json`

```json
"permissions": {
  "ask": ["Edit(src/**)", "Write(src/**)", "Edit(lib/**)", "Write(lib/**)"],
  "deny": ["Bash(git push:*)"]
}
```

Лид **спрашивает** перед записью прод-кода. Это не запрет, а стоп-кран: в момент, когда
он собирается «просто быстро поправить», пользователь видит вопрос и может ответить
«нет, напиши карточку».

**Строгий режим.** Если хочется настоящей границы — перенесите эти строки из `ask` в
`deny`. Тогда лид физически не сможет писать код, и эскалация всегда будет означать
дробление карточки. Минус: при реально сложной задаче процесс упрётся; снимать `deny`
придётся вручную.

## Что делать с `build` и `plan` в opencode

У opencode есть свои встроенные агенты (`build`, `plan`, `general`). Они остаются
доступны и подчиняются тем же правам из `opencode.json`, но **не** знают про дисциплину
карточек. Работайте через `implementer` / `fixer` / `test-writer`; встроенные держите
для разовых задач вне процесса.

Хотите закрыть и их — добавьте в `opencode.json`:

```json
"agent": { "build": { "disable": true }, "plan": { "disable": true } }
```

## Сигналы, что разделение сломалось

- Лид всё чаще правит код сам → карточки слишком крупные, вернитесь к `/dp:tasks`.
- Исполнитель регулярно пишет `outcome: blocked` → в разделе Context не хватает данных.
- Ревью проходит с первого раза всегда → карточки слишком мелкие, вы теряете скорость.
- В `git status` файлы, которых нет в `allowed_paths` → права настроены не так,
  проверьте `bash scripts/doctor.sh`.
