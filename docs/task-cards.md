# Карточки задач

Карточка — контракт между лидом и исполнителем. Исполнитель — сабагент Claude Code на
Sonnet: у него есть Read/Grep/Glob в этом репозитории, он не слепая модель без контекста.
Но он не исследует по своей инициативе и не помнит предыдущих задач — всё, на что карточка
не указывает явно (файлом, строкой или записью в `docs/knowledge/`), для него не существует.

Шаблон: `docs/.templates/task-card.md`.

## Анатомия

```yaml
---
id: T-003
feature: 001-token-refresh
title: Add token refresh to AuthClient
status: todo
depends_on: [T-001]
attempt: 0
agent: dp-implementer
model: sonnet
allowed_paths:
  - src/auth/client.ts
  - src/auth/client.test.ts
verify: "npm test -- src/auth"
knowledge_refs:
  - docs/knowledge/modules/auth.md
---
```

| Поле | Зачем |
| --- | --- |
| `id` | ссылка из `tasks.md`, ревью, отчёта, коммита |
| `depends_on` | `prepare-delegation.sh` не подготовит задачу, пока зависимости не `done` |
| `attempt` | инкрементируется автоматически; на `max-attempts` из конституции блокирует запуск и требует эскалации |
| `agent` | `dp-implementer` — код, `dp-test-writer` — только тесты, `dp-fixer` — доработка по ревью |
| `model` | обычно `sonnet`; можно поднять до `opus` разово для по-настоящему трудной задачи |
| `allowed_paths` | границы задачи, принуждаются хуком `.claude/hooks/dp-guard.sh` — не только описание |
| `verify` | ровно одна команда, определяющая «готово» |
| `knowledge_refs` | необязательно — файлы `docs/knowledge/modules/*.md`, которые стоит прочитать первыми |

Тело карточки: `Goal` · `Context` · `Files you may touch` · `Step-by-step` ·
`Acceptance criteria` · `How to verify` · `Out of scope — do NOT` · `When you are done` ·
`If you get stuck`.

## Шесть правил

### 1. Одна карточка — ≤ 3 файла и ≤ ~200 строк диффа

Не потому что модель не осилит больше текста, а потому что качество падает нелинейно:
на пятом файле она забывает, что решила на первом. Крупная задача дробится, даже если
дробление выглядит искусственно.

### 2. Context — указывает точно, а не пересказывает

Исполнитель умеет читать файлы. Вставлять в карточку то, что он и так может прочитать —
чистая трата токенов, а не мера предосторожности: это правило перевернулось по сравнению с
подходом, рассчитанным на модель без доступа к репозиторию.

Плохо:

> Добавь метод refresh по образцу существующих методов клиента.

(Слишком расплывчато — непонятно, какой файл, какой контракт, какое поведение при ошибке.)

Хорошо:

> `src/auth/client.ts:12` — класс `AuthClient`, метод `login()` как образец стиля.
> `docs/knowledge/modules/auth.md` — контракт `TokenStore` и формат `Token`.
> Эндпоинт `POST /auth/refresh`: на 401 сервер отдаёт `{ error: "invalid_refresh" }` — это
> не видно из кода, только из API-документации, поэтому здесь написано явно.

Вставляйте инлайном только то, что чтением файла не восстановить: решение, внешнее
ограничение, поведение стороннего сервиса, договорённость, которой ещё нет в
`docs/knowledge/`. Всё остальное — точный `file:line` или ссылка в `knowledge_refs`.

### 3. `allowed_paths` — точные пути

Никаких `src/auth/*`. Перечисляются конкретные файлы, включая те, которые будут созданы.
Список — не только чек-лист для ревью: хук `dp-guard.sh` сверяет реальные правки с ним же,
и всё, чего в списке нет, физически не редактируется.

### 4. Ровно одна команда `verify`

Она должна **уже работать** в репозитории — проверьте её сами перед делегированием.
Если команду назвать невозможно, задача не готова к делегированию: непонятно, по какому
признаку исполнитель поймёт, что закончил.

Плохо: `npm test` на весь проект (долго, шумно, чужие падения).
Хорошо: `npm test -- src/auth` — узко и быстро.

### 5. «Out of scope — do NOT» пишется явно

Модели заполняют тишину инициативой. Явный список запретов дешевле, чем ревью,
на котором вы обнаружите отрефакторенную половину модуля.

Базовый набор уже в шаблоне: не трогать зависимости, не рефакторить вне `allowed_paths`,
не лезть в `docs/` и `.claude/` (и то, и другое хук блокирует физически), не запускать git,
не «улучшать» прочитанное попутно, не исследовать репозиторий за пределами указателей.

### 6. Критерии приёмки — по ID из спеки

`AC-1`, `AC-2` копируются из `spec.md`. Тогда ревью механическое: каждый ID либо закрыт
с доказательством `file:line`, либо нет.

## Как дробить

**По слоям.** Модель данных → репозиторий → сервис → HTTP-хендлер → UI. Между слоями
контракт из `contracts/`, поэтому задачи не мешают друг другу.

**По критериям приёмки.** Один `AC` — одна задача, если он тянет на самостоятельный
кусок.

**Код и тесты отдельно** — если тестов много: `dp-implementer` пишет реализацию,
`dp-test-writer` покрывает её, с `depends_on`.

**Не дробите** то, что нельзя проверить по отдельности. Если после T-001 ничего не
запускается, значит граница проведена не там.

## Пример хорошей карточки

```markdown
---
id: T-003
feature: 001-token-refresh
title: Add refresh() to AuthClient
status: todo
depends_on: [T-001]
attempt: 0
agent: dp-implementer
model: sonnet
allowed_paths:
  - src/auth/client.ts
  - src/auth/client.test.ts
verify: "npm test -- src/auth/client.test.ts"
knowledge_refs:
  - docs/knowledge/modules/auth.md
---

## Goal
Метод `AuthClient.refresh()` обменивает refresh-токен на новую пару и сохраняет её.

## Context
- `src/auth/client.ts:12` — класс `AuthClient`, конструктор и `login()` как образец стиля
- `docs/knowledge/modules/auth.md` — контракт `TokenStore` и формат `Token`
- на 401 от `/auth/refresh` сервер отдаёт `{ error: "invalid_refresh" }` — не в коде,
  только в API-доке партнёра, поэтому здесь явно

## Files you may touch
| src/auth/client.ts | modify | только добавить метод refresh() |
| src/auth/client.test.ts | modify | добавить тесты, существующие не трогать |

## Step-by-step
1. Добавь `async refresh(): Promise<Token>` в `AuthClient`.
2. Возьми токен из `this.store.get()`; если `null` — брось `AuthError("no session")`.
3. `POST /auth/refresh` с телом `{ refresh }`.
4. При 401 очисти store и брось `AuthError("invalid_refresh")`.
5. При успехе сохрани через `this.store.set()` и верни новый Token.
6. Тесты: успех, отсутствие сессии, 401, сетевая ошибка.

## Acceptance criteria
- [ ] AC-1 — истёкший токен обновляется без повторного логина
- [ ] AC-2 — невалидный refresh очищает сессию и бросает AuthError

## How to verify
npm test -- src/auth/client.test.ts

## Out of scope — do NOT
- не трогай login() и logout()
- не добавляй зависимости
- не меняй интерфейс TokenStore
```

## Чек-лист перед делегированием

- [ ] ≤ 3 файла, ≤ ~200 строк
- [ ] Context указывает точно (`file:line`, `knowledge_refs`), не пересказывает то, что
      исполнитель прочитает сам
- [ ] `allowed_paths` — точные пути, включая создаваемые файлы
- [ ] `verify` проверена вручную и проходит на текущем коде (падая по нужной причине)
- [ ] «Out of scope» заполнен
- [ ] критерии приёмки указаны по ID из `spec.md`
- [ ] `depends_on` содержит только реальные зависимости
